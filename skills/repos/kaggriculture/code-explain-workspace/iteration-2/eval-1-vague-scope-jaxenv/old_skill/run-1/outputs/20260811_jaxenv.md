## 概要

`jaxenv` は Kaggriculture の公式エンジン（`kaggle-environments`）を **JAX で書き直したバッチ環境**である。公式エンジンは状態をネストした Python dict とタイルごとの `dict` オブジェクトで保持しており、そのままではアクセラレータに載らない。そこで全フィールドを先頭に batch 軸 `B` を持つ密な配列（struct-of-arrays）に再表現し、`B` 個の環境を 1 回の `jax.jit` 済み `step` で同時に進める。

ラッパーではなく**再実装**なので、`simulate.fast`（エンジンのインタプリタを直叩きする実装）にはない乖離リスクを抱える。それを担保しているのが公式エンジンとの等価性テストだけである。

外から見た入口は 2 つ。ライブラリとしては `simulate.jaxenv.env.step` / `simulate.jaxenv.state.initial_state`、CLI としては `python -m simulate.jaxenv.benchmark` である。目的は「GPU バッチ化が本当に割に合うのか」を測ることで、ゲームの全機能ではなく **作物・市場のコアだけ**を移植している。

## 1. ディレクトリ構成

```
backend/src/simulate/jaxenv/
├── __init__.py     空ファイル（0 行）。再エクスポートは一切なく、名前空間の宣言のみ
├── state.py        EnvState（バッチ状態の NamedTuple）、ゲーム定数、市場価格関数、初期状態生成
├── env.py          jit 済み step 本体。ユニット操作 / 市場 / 枯死 / 日次処理をマスク更新で実装
├── town.py         町ショップ解禁スケジュールをホスト側で再現し、需要テーブルに変換
└── benchmark.py    official / fast / jax の 3 エンジンをスループット比較する CLI
```

**エントリポイント**

| 入口 | 用途 |
|---|---|
| `state.initial_state(batch_size)` | 初期 `EnvState` を作る。ここから始める |
| `env.step(state, op, crop_arg, market_op, market_item, market_qty)` | 1 ターン進める。`@jax.jit` 済み |
| `state.market_price(inventory)` | 在庫から価格を求める。単体でも使える（テストが直接叩いている） |
| `town.shop_demand_table(seed, days, ...)` | ショップ需要テーブル。**現状 `env.py` からは呼ばれていない**（後述） |
| `python -m simulate.jaxenv.benchmark` | ベンチマーク CLI（`--steps` / `--batches` / `--json` / `--skip-cpu`） |

`__init__.py` が空なので、利用側は必ず `from simulate.jaxenv import env as E` / `from simulate.jaxenv.state import ...` のようにサブモジュールを名指しする。テストもそう書かれている。

**依存方向**

```
state.py  ←  env.py  ←  benchmark.py
   ↑                        │
   └── town.py              └── ..config (MatchSpec) / ..fast / kaggle_environments
```

- `state.py` は `jax` 以外に依存しない最下層。
- `env.py` は `state.py` のみに依存する。**`town.py` には依存していない。**
- `benchmark.py` だけが親パッケージ（`simulate.config`, `simulate.fast`）と `kaggle_environments` を参照する。しかもそれらは関数内 import で、モジュール読み込み時には引かれない。

**ここに無いもの**

- **ポリシー・エージェント**は無い。`benchmark.py` の `rollout` 内に、時刻だけで決まるスクリプト（小麦ループ）がハードコードされているだけ。
- **公式エンジンとの照合**は `backend/tests/e2e/src/simulate/test_jaxenv_equivalence.py` にある。この再実装を信用してよい根拠はコード側ではなくテスト側にある。
- **GPU の測定結果と考察**は `docs/plans/simulator/jax-gpu.md`（CUDA で 42,900x、Metal では逆に遅い）。
- **未実装のゲーム要素**: 雇い人（hands）、動物、肥料、`BUY_LAND`、雑草の自然発生、町ショップの実適用。

## 2. クラス / メソッド一覧

### 2.1 中核オブジェクト: `EnvState`（state.py:124）

`NamedTuple` なので JAX の pytree として自動的に扱われ、`tree_map` や `fori_loop` の carry にそのまま渡せる。更新は `state._replace(...)` による純粋な作り直し。

| フィールド | 形状 / dtype | 意味 |
|---|---|---|
| `step` | `(B,)` int32 | 経過ターン。`day = step // 24`、`hour = step % 24` はプロパティ |
| `money` | `(B, 2)` float32 | 所持金。金額のみ float32、他は int32 |
| `kind` | `(B, 2, H, W)` int32 | タイル種別（`KIND_EMPTY/PLANT/WEED/LOCKED/COOP/PASTURE`） |
| `crop` | `(B, 2, H, W)` int32 | 作物コード。未植は `CROP_NONE = -1` |
| `planted_day` | 同上 | 植えた日 |
| `watered_today` | 同上 | その日水をやったか（0/1） |
| `consecutive_unwatered` | 同上 | 連続無水日数。2 で雑草化 |
| `yield_units` | 同上 | 収穫可能な単位数 |
| `max_lifespan_step` | 同上 | 枯死開始ステップ。継続収穫作物は `-1`（無期限） |
| `farmer_x` / `farmer_y` | `(B, 2)` int32 | 農夫の位置。hands は未実装 |
| `shed` | `(B, 2, 9)` int32 | 納屋在庫（製品 9 種） |
| `carried` | `(B, 2, 9)` int32 | 手持ち。日終わりに納屋へ落ちる |
| `seeds` | `(B, 2, 5)` int32 | 種の所持数（作物 5 種） |
| `market_inv` | `(B, 9)` int32 | **共有**市場在庫。プレイヤー軸が無いのが要点 |

タイルは「オブジェクトの配列」ではなく **プレーン（面）の集合**である。1 タイルの属性ごとに `(B, 2, H, W)` の配列が 1 枚ずつあり、タイル単位の分岐は `jnp.where` によるマスク更新に化ける。

| `MARKET_I0 = 10_000`, `PRICE_FLOOR = 1`, `SHED_CAPACITY = 100`, `TURNS_PER_DAY = 24`, `STARTING_MONEY = 3000` | ゲーム定数 |

## 3. 処理ステップ

### 3.1 1 ターンの流れ（`env.step`）

```
1. day = state.step // 24 を求める                                (env.py:420)
2. 農夫の足元が LOCKED なら、そのターンのタイル操作を PASS に潰す
   （移動だけは潰さない → tile_op と op の 2 系統になる）        (env.py:422-424)
3. _apply_moves: op が方角なら移動。盤外なら位置据え置き         (env.py:426 / 99)
4. _apply_plant: 移動後の足元に植える                             (env.py:427 / 110)
5. _apply_water: 水やり + ボーナス窓なら収量 +1                   (env.py:428 / 176)
6. _apply_harvest: 成熟株を carried へ                            (env.py:429 / 208)
7. _apply_dig: 作物 / 雑草を除去                                  (env.py:430 / 235)
8. _process_market: 1 単位ずつ 32 回ループして注文を決済          (env.py:432 / 254)
9. _town_consume: step % 24 == 0 なら町の中心が各 1 消費          (env.py:433 / 326)
10. _decay_plants: 寿命超過株の収量を削る                          (env.py:434 / 333)
11. closes_day = (step+1) % 24 == 0 のときだけ _end_of_day を採用
    （常に計算し、tree_map + where で採否を選ぶ）                 (env.py:436-444)
12. step += 1                                                     (env.py:446)
```

3〜7 が「移動してから同じターンに足元を操作する」順序になっている点は重要で、`PLANT` などのタイル操作は **移動後の**タイルに効く。ただし 2 の LOCKED 判定は **移動前の**足元で行われている（`_apply_moves` の呼び出しより前）。移動と操作を同時に指定するアクション表現ではこの差が効く。

### 3.2 市場決済が逐次ループである理由（`_process_market`, env.py:254）

エンジンは両プレイヤーを**同一のコミット前在庫**に対して見積もり、そのうえで 1 単位ずつ順にコミットする。この逐次依存は本物なので、ベクトル化で消すのではなく `jax.lax.fori_loop` で固定長 32 回のループを回している。トレース形状を静的に保つための固定長であり、**方針が 32 を超える数量を要求すると超過分は静かに落ちる**。

1 単位あたりの処理:

```
prices    = market_price(market_inv)        ← 毎単位で価格を再評価
can_sell  = 注文が SELL かつ 納屋に在庫あり
can_buy   = 注文が BUY_SEED かつ 所持金 >= 種代
売り: shed -1、money += 価格、market_inv += 1（ただし価格が 1（下限）なら在庫は増えない）
買い: money -= 種代、seeds += 1（market_inv は動かさない = 種は市場から引かれず「発行」される）
成立した側だけ remaining を 1 減らす。成立しなければ remaining は 0 にされ打ち切り
```

`market_inv` はプレイヤー軸を持たないので、売却分は `inv_delta.sum(axis=1)` で 2 人ぶんを合算して加える。これが「両者が同じ板に売り込む」という競技のコアを表現している部分である。

### 3.3 日締め処理（`_end_of_day`, env.py:351）

```
1. 水をやっていない株の consecutive_unwatered を +1、やった株は 0 に
2. 連続 2 日無水の株は雑草化（kind=WEED, crop=NONE, yield=0）
3. 継続収穫作物（TOMATO / STRAWBERRY）は
   since_first = 翌日 - planted_day - first_yield_day が 0 以上かつ
   interval の倍数で、通算回数が max_yield 以下なら収量 +1
4. carried を shed に落とす。容量 100 を超える分は破棄
   （cumsum で製品順に詰め、入り切らない後ろの製品から落ちる）
5. 農夫を初期位置 (4,4) に戻す
6. watered_today を全クリア、carried をゼロに
```

4 の実装は `cumsum` を使った「製品インデックス順に詰められるだけ詰める」方式で、どの製品が捨てられるかは**製品の並び順**で決まる。エンジンと同じ順序であることが前提になっている。

### 3.4 分岐と条件付き適用

Python レベルの分岐は一切なく、すべて次の 3 パターンに帰着する。

- **マスク付き `jnp.where`** — 個別のルール（`ok` を作って適用可否を選ぶ）
- **`take_along_axis` によるテーブル選択** — `_shape_fn` の 5 種類の形状関数
- **`tree_map` による状態まるごとの採否** — `_end_of_day` は毎ターン計算され、日締めのターンだけ結果が採用される（env.py:438-444）

3 番目は「日締めでないターンでも日締め処理の計算コストを払う」ことを意味する。分岐を許さない代わりに常に最悪ケースを実行するという、この移植全体の設計思想がいちばん露骨に出ている箇所である。

### 3.5 副作用

- **`env.py` / `state.py` は完全に純粋。** ファイル IO もネットワークも、モジュール外の可変状態も持たない。
- **`town.py`** は `random.Random` を関数内で新規に作るため、グローバル RNG は汚さない。ただし `rng.random()` を空回しして乱数列を進めるという副作用込みの再現を行っている。
- **`benchmark.py`** のみ `print` と `--json` でのファイル書き込みを行い、`kaggle_environments` を実際に走らせる。

### 3.6 エラー処理

明示的な `try` / `except` は 1 つも無い。設計として**すべての違反は例外ではなくマスクで潰される**。

- 不正な操作（空でないタイルへの `PLANT`、種切れ、資金不足、未成熟株の `HARVEST`）→ `ok` が `False` になり、単に何も起きない
- 盤外への移動 → 位置が据え置かれる
- `market_qty > 32` → 超過分が黙って消える
- `tree_flatten_check` だけが唯一の明示的な検証で、しかも `step` からは呼ばれておらず、呼び出し側が任意に使うガードである

これは公式エンジンの「不正アクションはサイレント no-op」という仕様と揃っている一方、**バグが低スコアとしてしか現れない**という同じ落とし穴も引き継いでいる。

## 補足

### スコープの限界（過大評価しないための注意）

`env.py` の docstring が明示している未実装項目:

- プレイヤーごとに農夫 1 人のみ。雇い人（hands）なし
- NW 象限のみ。`BUY_LAND` は未実装
- 動物・肥料・町ショップなし
- 雑草の自然発生なし（タイルごとの RNG が必要。`weedSpawnChance` は 0.005）

市場操作も `SELL` / `BUY_SEED` の 2 つ、しかも 1 ターン 1 注文だけである（本来は 1 ターン最大 10 注文）。したがってベンチマークの数値は「完全な移植が 1 ステップあたりに払うべき仕事量の**下限**」であり、`benchmark.py` の docstring 自身がそう断っている。

### `town.py` は書かれているが接続されていない

`env.py` の `_town_consume` は**町の中心**（`_TOWN_CENTER_MASK`、24 ステップ間隔）だけを実装しており、`town.py` の `shop_demand_table` を呼んでいない。`town.py` はホスト側で需要テーブルを作れる状態で置かれているが、現状ステップ関数には配線されていない。ここは「読める形で用意されているが未使用」というギャップなので、`town.py` があるからショップが動いていると誤読しないこと。

その理由も `town.py` の docstring に書かれている。ショップ解禁の抽選は `_spawn_weeds` と RNG ストリームを共有しており、**空きタイル数に応じて消費される乱数の個数が変わる**（実測で 1 日目 50 draw、雑草が 1 つ出ると 49、もう 1 つで 48）。つまり盤面が事前に読めない限りスケジュールを先に表にできない。スクリプト方針なら成立するが、任意のプレイでは成立しない。

### エンジン仕様に関する 2 つの注記（コード内コメント由来）

1. **町の中心は 1 個しか消費しない。** `env.py:320-323` が「`docs/competition/abstract.md` の要約と違い、このエンジンのバージョンには日数ベースの倍率が無い。抽象ドキュメントではなくエンジンを読んだ結果である」と明記している。仕様の食い違いに気づいたうえで**エンジン側を正**としている。
2. **丸めは銀行家丸めではない。** `market_price` は `jnp.round` を使わず `jnp.floor(price + 0.5)` を使う（state.py:199-202）。エンジンの Python `round` → `int` が正値に対して行う挙動と合わせるためで、`jnp.round` にすると .5 の境界で 1 ずれる。価格が整数丸めされるゲームなので、この 1 ずれが等価性テストを落とす。

### JAX 環境そのものに関する落とし穴

- **`jax` は `pyproject.toml` に入っていない。** `kaggle-environments` が直接依存しているので、エンジンがある場所には必ず存在する（state.py:25-27）。意図的な非記載である。
- **`jax-metal` をこの venv に入れてはいけない。** `jax.devices()` を全テストで乗っ取ったうえ、このワークロードを CPU より約 100 倍**遅く**する（state.py:27-29）。`docs/plans/simulator/jax-gpu.md` の実測では Metal は CPU の約 1/118、公式エンジンより遅い 0.26x。原因は scatter で、CUDA にはこの問題が無い。
- **CUDA では狙いどおり効く。** RTX 4090 / batch 65536 で約 3,650 万 env-steps/s、公式比 42,929x。飽和点は 65536 付近で、262144 では低下する。
- **`n_steps` はトレース対象のまま渡す。** `benchmark.py:95-98` が「Python の int として焼き込むと XLA がエピソード長ごとに特殊化し、Metal では 0.3 秒のコンパイルが数分になった」と記録している。

### テストが唯一の担保

`backend/tests/e2e/src/simulate/test_jaxenv_equivalence.py` は `weedSpawnChance=0`、ショップ解禁間隔を `10**6` に設定して**両エンジンで確率要素を消し**、決定論的なコア（作物、水やり、収穫、市場価格、町の中心需要、日締め精算）だけを比較する。`jax` は `pytest.importorskip` 越しの任意依存として扱われている。

再実装である以上、等価性は構造的に保証されない。このモジュールを触るときは、まずこのテストを通すことが正当性の定義そのものになる。
